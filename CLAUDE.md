This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Or Litany's personal academic homepage, served as a static site via GitHub Pages (`orlitany.github.io`), built with Astro. It also contains Python tooling that generates a LaTeX CV (`latex/cv.pdf`) from the same data that feeds the website, so the site and the CV stay in sync.

The Astro project lives in `site/`; everything else at the repo root (`cv_files/`, `generate_cv.py`, `latex/`) is shared between the website build and the CV generator.

## Running locally

```
cd site
npm install
npm run dev
```

Then visit `http://localhost:4321/`. `npm run build` produces a static `site/dist/`; `npm run preview` serves that build locally.

## Generating the CV PDF

```
python3 generate_cv.py
```

This reads `cv_files/publications.bib`, `cv_files/workshops.json`, and `cv_files/students.json`, regenerates `latex/publications.tex`, `latex/workshops.tex`, and `latex/advising.tex`, then compiles `latex/cv.tex` with `tectonic` (must be installed and on `PATH`) to produce `latex/cv.pdf`. Bio/education/experience sections of `cv.tex` are static and not regenerated by this script. Requires `bibtexparser` (`pip install -r requirements.txt`).

There is a separate, gitignored `local_internal_cv/` directory with `generate_cv_internal.py` for a private Technion-only CV variant — bootstrap it with `--init` from `latex/`. Do not un-gitignore this directory.

## Architecture

**Data flow:** All dynamic content (publications, talks, workshops, press, news, courses, students) lives under `cv_files/` at the repo root — shared by both the website and `generate_cv.py`. Astro's Content Layer API (`site/src/content.config.ts`) loads each source through a custom loader in `site/src/lib/loaders/`, validates it against a Zod schema, and renders it at build time — a malformed entry fails the build with a clear error rather than silently breaking a page section. There's no client-side fetching; the page ships as static HTML with a handful of small `<script>` islands for interactivity (show-more toggles, tabs, the dark-mode toggle, BibTeX copy button).

**Publications are BibTeX-first:** `cv_files/publications.bib` is the single source of truth — adding a paper means adding one BibTeX entry. Custom (non-standard) fields on each entry carry site-specific metadata: `venue` (a hand-written display string like `"CVPR 2026"` or `"Preprint"` — not reliably derivable from standard `booktitle`/`journal` fields), `image`, `paper`, `code`, `page`, `poster`, `slides`, `talk`, `video`, `dataset`, `tweet`, and `award` (a plain-text badge, e.g. "Best Paper Award"). `site/src/lib/loaders/bibtexLoader.ts` parses it with `@retorquere/bibtex-parser` — **pinned to a `9.x` version**; the current `10.x` `latest` on npm has a broken types publish. Publications are sorted for display by the year embedded in `venue` (falling back to the bib `year` field for preprints), not by the raw bib `year`, since that's often just the arXiv posting year rather than the year the paper actually appeared — see `site/src/components/Publications.astro`.

**`cv_files/students.json` keeps its original `{ current: [...], alumni: [...] }` shape** (read directly by `generate_cv.py`); the Astro `students` collection loader flattens it into one array with a `status` field at load time rather than reshaping the source file.

**Editing site content:** add/change a publication by editing `cv_files/publications.bib`; everything else (talks, workshops, press, news, courses, students) by editing the corresponding JSON file in `cv_files/`. Never hand-edit generated HTML.

**CV generation reuses the site's data:** `generate_cv.py` parses the same `cv_files/publications.bib` (via `bibtexparser`) and the same JSON files as the website. When changing the shape of a data source (e.g. adding a field to a publication or student entry), check both the Astro schema/component in `site/src/` and `generate_cv.py`, since they parse the same source independently and will silently ignore fields the other doesn't know about. Note `latex/talks.tex` is `\input` by `cv.tex` but has no generator counterpart — it's hand-maintained and can drift out of sync with `cv_files/talks.json`.

**Deployment:** `.github/workflows/deploy.yml` builds `site/` with `withastro/action` and deploys via `actions/deploy-pages` on every push to `master`. GitHub Pages is configured to deploy from GitHub Actions, not from a branch — files at the repo root (other than `site/`) are not served directly. The `prebuild` npm script copies `../latex/cv.pdf` into `site/public/latex/` so the CV PDF ships with the build; the Google Search Console verification file lives at `site/public/google0ea1515340d2024d.html` for the same reason.

**Styling:** `site/src/styles/global.css` holds design tokens (CSS custom properties, including a `[data-theme='dark']` override) and base styles; most components carry their own scoped `<style>` block.

**`helper_functions/`** contains a legacy notebook (`json_to_latex.ipynb`, `pdf_downloader.ipynb`) not part of the regular generation flow, plus `fetch_patents.py` which scrapes Google Patents to produce `cv_files/patents.json` (not currently wired into the site).

## Notes

- `example_cv.json` is a template/reference schema, not live data.
- `notes.txt`, `read_json.ipynb`, and `publications_backup.js` are gitignored scratch files if present locally.
- SEO/social metadata (Open Graph, Twitter cards, JSON-LD `Person`/`WebSite` schema) is defined in `site/src/layouts/Base.astro` — update it there if bio facts (title, affiliation, awards) change, since it's duplicated from the bio text in `Bio.astro`.
